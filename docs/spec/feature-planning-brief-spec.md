# 작은 기능 기획 + 프로젝트 브리프 (설계 노트 · 스케치)

> Drafting 은 PM 도구가 아니다(프로젝트 관리 X). 다만 **이미 있는 제품에 작은 기능을 기획**하는 건 자주 필요하다.
> 핵심 난제 두 가지: ① 프라이빗 레포 권한 ② 기존 코드와 신규 기획의 **정합성**(안 맞으면 토큰 낭비).
> 결론: 그린필드 체인을 억지로 재사용하지 말고, **프로젝트 브리프(맥락) → 가벼운 기능 문서**로 별도 흐름을 둔다.
> 상태: 구현 X · 생각 정리 + 유저 플로우 사전 점검용.

## 1. 프라이빗 레포 권한 — 로컬 폴더 읽기

Drafting 은 로컬/셀프호스트, 사용자는 그 레포를 **이미 로컬에 클론**해 놓았다 →
- **1순위: 로컬 레포 폴더 경로 지정.** GitHub 인증 불필요, 프라이빗 무관, 로컬-퍼스트 정합.
- 차선(원격만): GitHub PAT(repo scope) 암호화 저장(BYOK 계보). 시크릿 비용 있어 비권장.
- "GitHub 링크 읽기"보다 **폴더 지정**이 이 제품에 맞다.

## 2. 정합성 — 레포 통째 X, 압축 브리프 O

레포 전체를 먹이면 토큰 낭비 + 노이즈로 오히려 엉뚱한 참조. 100% 정합은 "많이"가 아니라 "딱 필요한 것".

- **프로젝트 브리프(1회 추출·재사용)** = 스택 · 아키텍처 · **네이밍 컨벤션** · 기존 기능 목록 · 핵심 용어 · 제약.
  로컬 레포에서 README·매니페스트·디렉터리 구조·엔트리 파일만 읽어 **압축**(전체 코드 X).
- 기능 기획은 **레포가 아니라 이 브리프를 상위 맥락**으로 참조 → 실제 스택·이름 반영 + 토큰 절약.
- 기능이 특정 모듈만 건드리면 그 **슬라이스만** 추가.
- 브리프는 제안→수락(사람이 검수·편집) + **staleness**(코드 바뀌면 갱신 · Drafting 부모-stale 계보).

## 3. 정합성 lint (낭비 방지 장치)

Drafting 의 링크 위반 lint 와 같은 원리:
- 기능 기획이 브리프에 **없는 모듈/용어를 참조** → 경고("기존에 없는데 맞나?"). **차단 아님(advisory)** — 신규 도입은 정당할 수 있으니.
- "그럴듯하지만 코드와 안 맞는" 기획을 조기 차단 → 토큰·시간 낭비 방지.

## 4. 기능 문서 = 가볍게 (체인 강요 X)

작은 기능에 PRD→스펙→IA→플로우→디자인시스템 6종은 과하다. **가벼운 단독 문서**:
- 필드: 배경 · 현재 동작(as-is) · 바꿀 것 · 영향 범위 · 수용 기준. (선택: 영향받는 화면 몇 개)
- 상위 맥락 = 프로젝트 브리프(있으면) / 없으면 범용 PRD 수준.
- 산출: **핸드오프 프롬프트 팩** — 코딩 에이전트(Claude Code)가 **실제 모듈명·컨벤션**으로 바로 작업.

## 5. 유저 플로우 (구현 가정)

1. 새 **기능 기획** 만들기.
2. (선택) **프로젝트 브리프 붙이기** — 로컬 레포 폴더 지정 → 브리프 추출 → 검수·수락. (또는 붙여넣기 / 건너뛰기)
3. 기능 인터뷰(배경·현재 동작·변경·영향·수용 기준) — 브리프를 맥락으로.
4. 생성 → 기능 문서(브리프에 정합). 정합성 lint 경고 검토.
5. 수락 → 핸드오프 프롬프트 팩(실제 모듈 참조) → 코딩 에이전트로.

## 6. ⚠️ 유저 플로우 사전 점검 — 실제 쓸 수 있나 (정직하게)

**되는 점**
- 프라이빗 권한 문제를 **로컬 폴더 읽기로 우아하게 소거**(가장 큰 걱정 해소).
- 브리프는 **1회·재사용**이라 여러 기능에 비용 분산.
- 페이오프가 명확: **실제 코드베이스에 맞는 핸드오프** → CLI provider 로 Claude Code 바로 구동(기존 자산 재사용).

**마찰·리스크 (실사용 걸림돌)**
- **[체인 불일치]** 기존 6종 체인은 작은 기능엔 과함 → **가벼운 단독 문서**가 별도로 필요(안 그러면 "작은 기능"인데 6단계 강요). *구조 변경 필요.*
- **[브리프 품질이 전부]** 브리프가 얕거나 틀리면 하류 전부 쓰레기 = 사용자가 말한 토큰 낭비. → **검수·편집 필수 + 추출 범위 신중**(README·매니페스트·구조 중심, 코드 전량 X).
- **[브리프 staleness]** 여러 달·여러 기능이면 코드와 드리프트 → **싼 갱신 + stale 표시** 필요.
- **[첫 실행 무게]** 처음엔 폴더 지정→브리프 추출→검수까지가 "작은 기능"치곤 무거움. → 브리프 재사용으로 완화되지만 초기 비용은 실재. **건너뛰기(범용 PRD) 경로 필수.**
- **[가치는 전적으로 브리프 그라운딩]** 브리프 없으면 = 지금 Drafting 의 범용 PRD 와 동일(신규 가치 0). 즉 이 기능의 값어치는 **브리프 정합성 하나에 달림**.

**판정**
- **원리적으로 사용 가능**하고, 로컬 폴더 읽기가 권한 난제를 깔끔히 푼다.
- 단, **"작은 기능 문서(체인 밖 단독) + 검수 가능한 브리프 + 정합성 lint + 건너뛰기 경로"** 4개가 함께여야 실제로 쓸 만하다.
  하나라도 빠지면 → 과한 흐름이거나(체인 강요) 토큰 낭비(브리프 미검수)로 무너진다.
- **다음 단계**: 이 4개를 최소 스코프로 좁힌 뒤 구현 착수. 지금은 스케치.

## 7. 단독 기능 문서 정의 (`feature` 타입 · 확정)

체인에서 **feature-spec 이 뼈대**. 거기에 기존 프로젝트용 2개(현재 동작 as-is · 영향 범위)를 얹고,
IA·유저플로우·디자인시스템·제품 PRD 는 뺀다. 상위 맥락 = **프로젝트 브리프(선택)**, 체인 독립(단독).

### 인터뷰 7문 (`api/templates/feature.json`)

| # | id | 질문(prompt) | 힌트 | 성격 |
|---|----|------|------|------|
| 1 | `background` | 이 기능이 왜 필요한가요? 지금 사용자는 이 부분을 어떻게 겪나요? | 현상의 불편(as-is pain) | 필수 |
| 2 | `as_is` | 지금 이 부분은 어떻게 동작하나요? (신규면 '없음') | 기존 동작·제약 | 필수 |
| 3 | `story` | 무엇을 만들거나 바꾸나요? 사용자 관점 한 문장으로. | "~로서 ~하고 싶다" | 필수 |
| 4 | `rules` | 핵심 동작 규칙·로직은? | 조건·분기·기본값 | 필수 |
| 5 | `acceptance` | 무엇이 되면 '완료'인가요? 측정 가능하게. | 체크 가능한 기준 여러 개 | 필수 |
| 6 | `scope` | 어느 모듈·화면·기능을 건드리나요? (기존 이름으로) | 브리프의 실제 이름 | 필수 |
| 7 | `edge` | 예외·경계·실패 케이스나 데이터 변화가 있나요? (없으면 '없음') | 엣지·데이터·상태 | 선택 |

- draftGuidance: "위 답변 + 프로젝트 브리프로 이 기능만의 기획을 만든다. 기존 스택·컨벤션·이름을 그대로 쓰고,
  브리프에 없는 모듈·용어를 새로 지어내지 마라. 수용 기준은 체크 가능하게."

### 산출 필드 (feature 문서)

```
Feature {
  title
  background          // Why (1)
  as_is               // 현재 동작 (2)
  story               // 유저 스토리 (3)
  rules: string[]     // 동작 규칙 (4)
  acceptance: string[]// 수용 기준 — 체크 항목 (5)  ← 핸드오프의 심장
  scope: {            // 영향 범위 (6) — 정합성 앵커
    modules: string[]   // 브리프 모듈 참조
    screens: string[]   // 영향 화면(선택, 1~2)
    features: string[]  // 관련 기존 기능
  }
  edge?: string[]     // 예외·경계 (7, 선택)
  data_changes?: string // 데이터/상태 변화 (7, 선택)
}
```

### 핸드오프 매핑 (코딩 에이전트가 받는 것)

`왜 background` · `지금 as_is` · `무엇을 story+rules` · `완료 acceptance` · `어디에 scope` → 실제 모듈명으로 바로 작업.

### 정합성 lint (advisory)

`scope.modules / features` 가 **브리프에 없는 이름**을 참조하면 경고("기존에 없는데 신규인가?").
차단 아님 — 신규 도입은 정당할 수 있으니 사람이 판단. 이게 "코드와 안 맞는 기획 → 토큰 낭비"를 조기 차단.

### 브리프 없이 쓰면

`scope` 는 자유 서술이 되고 정합성 lint 는 꺼진다 → 결과는 **범용 기능 PRD** 수준(그것도 쓸모, 단 신규 가치는 브리프에 있음).
